# Autos Alemanes · Costa del Sol

App local para buscar, puntuar y seguir coches alemanes (Mercedes-Benz, BMW, Audi, Volkswagen, Porsche) en Alemania y revenderlos en la Costa del Sol. Backend FastAPI + SQLAlchemy (SQLite), frontend React + Vite + Tailwind 4. UI y textos en español; términos de búsqueda en alemán (Marke, Modell, Erstzulassung, Kilometer, Preis, Ort oder PLZ, Kraftstoffart, Getriebe).

## Arranque

**Uso diario:** `scripts/instalar-agente.sh` instala un agente de launchd (`com.autos-alemanes.costa-del-sol`) que mantiene el backend en `127.0.0.1:8000`, y este sirve también la interfaz compilada (`frontend/dist`, hay que `npm run build` tras cambiar el frontend). `scripts/abrir.command` abre la app. Registro: `~/Library/Logs/autos-alemanes.log`. **Tras cambiar código del backend hay que reiniciarlo**: `launchctl kickstart -k gui/$(id -u)/com.autos-alemanes.costa-del-sol`. Si el agente está instalado, el puerto 8000 está ocupado: para desarrollar con otro backend, `scripts/desinstalar-agente.sh` primero. Los scripts no llevan rutas personales (el repo es público): las calculan desde su ubicación.

**Desarrollo:**

```bash
cd backend && source .venv/bin/activate && uvicorn app.main:app --reload --port 8000
cd frontend && npm run dev          # http://localhost:5173, el proxy envía /api al backend
```

No pegues comentarios `#` al final de un comando en zsh interactivo: se pasan como argumento (Vite lo tomó como directorio raíz).

## Estructura

- `backend/app/scrapers/` — un scraper por fuente (`base.py` define `Scraper`, `ScrapedCar`). Implementados: `kleinanzeigen.py` y `autoscout24.py`.
- `backend/app/services/` — `mercado_es.py` + `rentabilidad.py` + `llm.py` (Analizar rentabilidad), `scope.py` (qué queda fuera de alcance), `dedupe.py` (anuncios duplicados), `sync.py` (scraping → upsert → scoring → vigencia, y estado de la sync en segundo plano), `scoring.py` (determinista), `llm.py` (rentabilidad, opcional), `settings_store.py`.
- `backend/app/routers/` — `/api/cars`, `/api/settings/{search|weights|app}`, `/api/sync`, `/api/sync/status`, `/api/sync/auto`.
- `frontend/src/` — `App.jsx` (dashboard, filtros, barra de sync), `CarCard.jsx` (tarjeta + seguimiento CRM), `Settings.jsx`.

## Cosas no obvias

**kleinanzeigen.de** (verificado contra el sitio real, puede cambiar):
- El filtro de ciudad solo se aplica con el id de ubicación `l<ID>` en la URL; sin él busca en toda Alemania. El id sale de `/s-ort-empfehlungen.json?query=<Ort o PLZ>` (Stuttgart = 9280).
- Los rangos usan `%2C`: `autos.ez_i:2010%2C2020`, `autos.km_i:50000%2C170000`. Con `:` el filtro se descarta en silencio.
- **Dañados:** la búsqueda lleva `autos.schaden_s:nein` ("Unbeschädigtes Fahrzeug"; `ja` = "Beschädigtes Fahrzeug"). Los nombres que se probaron a ciegas (`fahrzeugzustand_s`, `damaged_b`...) se ignoran en silencio: los filtros reales salen de los enlaces de la propia página de búsqueda. El detalle trae `Fahrzeugzustand: "ja"` y se usa como red de seguridad. `python -m app.maintenance purge-damaged [--dry-run]` (desde `backend/`) quita de la base los dañados guardados antes de tener el filtro, respetando los que tienen seguimiento.
- Marca: `autos.marke_s:<slug>` (`mercedes_benz`, `bmw`, `audi`, `volkswagen`, `porsche`). Con `k0` en la ruta, `preis:` se interpreta como texto de búsqueda; solo se usa `k0` si hay Modell.
- La lista no trae Getriebe, combustible, TÜV ni Klimaanlage: salen del bloque JSON de la página de detalle, que solo se pide para anuncios nuevos.
- **Anuncios borrados («Gelöscht»):** un anuncio que el vendedor borra deja de salir en las búsquedas pero su página sigue respondiendo HTTP 200 en la MISMA URL, y la versión de ESCRITORIO lo sigue mostrando normal (`adExpired:false`). Solo la versión **MÓVIL** (User-Agent de iPhone) pone `<div class="badge-unavailable">Gelöscht</div>` sobre cada foto de la galería (`imagegallery--list`) del propio anuncio. `inactive_urls` usa esa señal: vía rápida con una petición HTTP (~0,7 s, `ctx.request.get`) y, si no es concluyente (HTTP 403/429/5xx o error de red), respaldo cargando la página con el navegador. **Solo cuentan como retirado un 404/410, una redirección a la lista de búsqueda o la insignia; cualquier otro error HTTP es «no concluyente» (se da por vigente)**: antes cualquier HTTP ≥ 400 se tomaba por retirado, así que un bloqueo habría ocultado anuncios vivos. En una muestra de los 60 anuncios que llevaban más tiempo sin verse, el 23 % estaban borrados y no se detectaban; 0 falsos positivos en 25 vivos. `python -m app.maintenance verify-stale [--horas 12] [--dry-run]` aplica la verificación ya (marca `aktiv=False`, reversible; no toca el seguimiento). Un vendedor puede borrar y republicar (mismo coche, distinto id): el viejo se retira y el nuevo entra como anuncio nuevo. «Reserviert» no se trata (sigue activo).
- Ritmo: pausas de 1,5–3 s y máximo 4 páginas por marca. Una sync completa tarda 30–40 min la primera vez.

**autoscout24.de** (verificado contra el sitio real, puede cambiar):
- Lista y detalle traen un JSON `__NEXT_DATA__` con todos los datos: no se parsea HTML.
- Filtros por URL: `/lst/<marca>[/<modelo>]?fregfrom&fregto&pricefrom&priceto&kmfrom&kmto&zip&zipr&fuel=B,D&gear=A|M`. Se usa `sort=age&desc=1` (más recientes primero) y siempre `fuel`, que además excluye eléctricos.
- `zip` acepta PLZ o ciudad, pero si no reconoce el lugar lo sustituye en silencio por otro (Marbella → Malsburg-Marzell): `location_ok` lo detecta y la sync de esa fuente falla con un mensaje claro.
- TÜV (`nextVehicleSafetyInspection`), Klimaanlage (lista de equipamiento) y fecha de publicación solo están en el detalle, que se pide únicamente para anuncios nuevos.
- **Ojo con el reposo del Mac:** si el equipo se suspende (incluido el "Maintenance Sleep" nocturno) mientras corre una sync o una prueba, el navegador se congela y las páginas dan timeout aunque el sitio funcione (un `ping` con latencias de minutos delata el caso). Para syncs largas, mantenerlo despierto: `caffeinate -i -t 7200`. Una falsa alarma de "bloqueo anti-bot" por esto ya costó tiempo de diagnóstico.
- Un anuncio retirado redirige a `/lst/<marca>` (la URL final ya no contiene `/angebote/`).

**mobile.de: bloqueado.** Devuelve 403 "Zugriff verweigert" (anti-bot) a un navegador automatizado, con y sin User-Agent propio. No se intenta evadir. No volver a probarlo sin una vía legítima (p. ej. API de socio).

**Robustez de los scrapers** (`scrapers/base.py`): `retry` reintenta una vez ante timeouts de red/navegación; un HTTP de error (403...) se trata como bloqueo y aborta la fuente. Si falla la página de detalle de un coche, ese coche se descarta (no se guarda a medias: nunca se volvería a pedir su detalle) y se reintenta en la próxima sync; si fallan más de la mitad (mínimo 10), la fuente aborta. Al comprobar vigencia, un fallo de red deja el coche como vigente. Si falla una página de lista, la marca se corta ahí (se conserva lo leído) y se anota un aviso en `scraper.warnings`, que `run_sync` añade a `fehler` como "(aviso)"; solo se aborta la fuente si no carga ninguna marca, si hay un HTTP de error (bloqueo) o si el lugar no se reconoce. Tiempo máximo de carga por página: 60 s.

**Analizar rentabilidad** (botón por coche, bajo demanda; `POST /api/cars/{id}/rentabilidad` → 202, se consulta con `GET /api/cars/{id}` hasta que `rentabilidad.estado` pasa de `calculando` a `listo`/`error`; ~17 s medidos). Tres capas, y solo la última gasta tokens:
1. **Mercado en España** (`mercado_es.py`, scraping de `autoscout24.es`, sin tokens, caché de 3 días en `MercadoCache`). Verificado contra el sitio real: `cy=E` filtra España; la ruta `/lst/<marca>/<modelo>` con el texto del modelo que ya guardamos resuelve el modelo exacto (13 modelos probados); `fuel=B|D`, `gear=A|M`; el vendedor es `Dealer` o `PrivateSeller`. **Una cadena de concesionarios anuncia la misma unidad en varias sedes** (mismos km y precio, distinta ciudad y URL): se deduplica por (año, km, precio) SIN la localidad. Se hace una consulta amplia (año ±2, km ±50 %, mismo combustible; hasta 3 páginas) y la escalera de criterios (de estricto a laxo hasta tener 8 comparables) se aplica EN LOCAL sobre lo descargado: antes cada nivel era una consulta nueva y tardaba ~55 s. Los precios se ajustan al año/km del coche (+5,5 %/año, −0,3 %/1.000 km), se descartan atípicos (1,5 × IQR) y se informa de `confianza` (alta/media/baja según n y criterio) y de la mediana de particulares. Son precios de ANUNCIO: se aplica un descuento de venta (6 %). No funciona con modelo "Andere" (error claro) ni cuando AutoScout24.es nombra el modelo de otra forma (p. ej. Porsche 996).
2. **Margen** (`rentabilidad.calcular_margen`, aritmética exacta, sin tokens). Perfil `particular` o `empresa` (REBU = IVA 21 % solo sobre el margen; régimen general = IVA sobre el precio; compra a profesional con IVA deducible = compra sin IVA alemán y el REBU no aplica). Costes y porcentajes por defecto en `config.DEFAULT_RENTABILIDAD`, **todos editables en Ajustes** y solo orientativos (no es asesoramiento fiscal; no incluye IRPF/Sociedades ni ITP). El desglose (`lineas`) suma exactamente el margen. Rango pesimista/optimista con P25/P75. Veredicto numérico (Comprar/Dudoso/Descartar) con umbrales editables; con confianza baja nunca da "Comprar". El informe guarda `ajustes_hash` y la API marca `desactualizado` si cambiaron los costes después.
3. **Informe de IA** (`llm.py`, solo si hay una clave en `backend/.env`; ~2.500 caracteres de prompt, ~1.000 tokens por análisis, estimado). **Proveedores: Gemini (`google-genai`, SDK 2.x; `GEMINI_API_KEY`, `GEMINI_MODEL`) o Anthropic (`ANTHROPIC_API_KEY`, `LLM_MODEL`)**; `LLM_PROVIDER=auto` usa Gemini si hay clave de Gemini. Con Gemini se pide salida JSON con esquema (`response_schema`, `response_mime_type`); si el modelo rechaza el esquema (HTTP 400 "schema"), reintenta pidiendo solo JSON. `max_output_tokens=8192` porque en los modelos que razonan esos tokens cuentan dentro del límite; el informe guarda `uso` (proveedor, modelo, tokens de entrada, salida y razonamiento) y la tarjeta lo muestra. **Los nombres de modelo de Gemini cambian y las fuentes consultadas se contradecían** (hoy se retiran los 2.5, otra página lista 3.8/3.6 como estables): `python -m app.maintenance gemini-models` lista los que acepta la clave y `python -m app.maintenance probar-ia` hace una petición mínima para validar clave y modelo. Los errores se traducen a un mensaje accionable (400 clave/petición, 404 modelo, 429 cuota, 5xx caído) sin revelar la clave. Recibe los números ya calculados y solo valora y redacta (veredicto, puntuación, resumen, puntos fuertes, riesgos, qué revisar). El texto del anuncio es del vendedor: va aislado en un bloque delimitado y marcado como no fiable (anti prompt-injection) y la respuesta se valida (veredicto permitido, longitudes). Nunca lanza: si falla, queda el cálculo con un aviso. **Probado con la clave real (`gemini-3.8-flash`, existe en la lista de la cuenta)**: ~1.800-2.400 tokens por análisis (≈1.000 de entrada, ≈400 de salida y 300-1.400 de «razonamiento», que domina), 8-20 s con el mercado en caché. El modelo detectó cosas que los números no ven: avisos del propio anuncio («se vende en su estado actual», «muestra mensajes de error») y que el título contradecía el modelo registrado. También cometió fallos que se corrigieron en el prompt: sin la fecha de hoy trató un TÜV de 2028 como «imposible» (ahora el prompt lleva `Fecha de hoy` y explica que el TÜV dura 2 años) y escribió sin tildes (ahora se exige). Se verificaron sus afirmaciones contra los datos antes de fiarse. Si la IA discrepa del veredicto numérico, la tarjeta muestra los dos. `GET /api/settings/ia` informa (solo lectura) de qué IA está activa.
**Coherencia título/modelo** (`rentabilidad.conflicto_modelo`): el campo «Modell» de kleinanzeigen lo elige el vendedor y a veces contradice el título («B 200 CDI» registrado como «C 200», «A180» como «A 160», «Golf Plus» como «Golf»), con lo que los comparables eran de otro modelo y el margen salía mal sin avisar (+2.281 € «Comprar» que no era fiable). Reglas prudentes por marca (Mercedes letra+número, BMW número, Audi A/Q+dígito, VW Golf Plus/Variant/Sportsvan/Alltrack/Cabrio) que ignoran potencias («150 PS») y títulos más genéricos («A-Klasse»); afectan a ~2,4 % de los coches. Si saltan: aviso visible, confianza «baja» (la caché de mercado no se toca: se copia) y el veredicto numérico nunca da «Comprar». La IA recibe el aviso. Pendiente: corregir el modelo desde el título en vez de solo avisar.
Estados: `calculando` → `listo` | `error`; al arrancar, un `calculando` huérfano pasa a `error`. Los errores inesperados se registran con traza (`uvicorn.error`).

**Fuera de alcance** (`services/scope.py`): se descartan combustibles no deseados (eléctricos...) y **furgonetas de carga**. El criterio de furgoneta es conservador y solo usa indicios explícitos: modelo Sprinter/Crafter/Transporter/E-Load, o palabras completas del título (Kasten, Koffer, Kühlkoffer, Pritsche, Kastenwagen, NFZ, LKW). Un Caddy, Citan o Vito sin esas pistas se queda (pueden ser turismos): borrar un coche bueno es peor que dejar una furgoneta. Se aplica a los anuncios nuevos al guardarlos y, al arrancar el backend y tras cada fuente, borra los ya guardados que no cumplan, **salvo los que tienen seguimiento** (estado, notas o cita). Todas las filas "sin modelo" que había eran furgonetas.

**Duplicados** (`services/dedupe.py`): el mismo coche puede estar en los dos portales o repetido en uno. Las filas **no se borran** (la sync identifica anuncios por fuente + id externo y los recrearía): una es la principal y las demás tienen `duplicado_de` = id de la principal. La lista solo muestra principales, con `otros_enlaces`. Reglas conservadoras (un falso positivo esconde un coche distinto): misma marca, modelo, año, combustible y Getriebe, y (1) km idénticos + precio ±3 % + mismo sitio o km no redondo; (2) km ±0,3 % + precio ±2 % + mismo sitio o título parecido; (3) km ±0,1 % no redondos + precio ±2 %. "Redondo" = múltiplo de 100 (los vendedores redondean). Principal: la que ya tiene seguimiento (estado/notas/cita), luego la más completa, luego la más antigua. Se recalcula al arrancar el backend y tras guardar cada fuente; el índice de precios cuenta cada coche una sola vez. En la base real: 79 duplicados (59 entre portales, 20 en el mismo portal) de 963 activos.

**Migraciones:** `database.ensure_columns()` añade al arrancar las columnas nuevas a una base existente (`create_all` no altera tablas). Al añadir una columna al modelo, registrarla en `_ADDED_COLUMNS`.

**Sync y scoring:**
- Cada fuente se procesa y se guarda por separado: si una falla (bloqueo, cambio de web), las demás siguen y el error aparece en `fehler` del resultado y en la interfaz.
- Se descartan en `run_sync` los coches cuyo combustible no esté en `kraftstoffart` (p. ej. eléctricos), sea cual sea la fuente.
- La lista se sincroniza al abrir la app (`POST /api/sync/auto`, si alguna fuente supera `max_age_hours`) o con el botón. La sync diaria programada (`daily_sync`, `sync_hour`) existe pero está **desactivada por defecto**: en un Mac que se duerme no corre (el Mac solo despertaba 2-6 s cada ~17 min y la sync de las 7:00 caía sin red); está pensada para un servidor siempre encendido (p. ej. a las 5:00). Se activa/reprograma/quita en caliente desde Ajustes (`sync.apply_schedule`). Antes de cada sync se espera a que el DNS responda (hasta 90 s; tras despertar el Wi-Fi tarda en volver y fallaba con ENOTFOUND) y, en macOS, se lanza `caffeinate -i -s -w <pid>` mientras dura (no evita el reposo por cerrar la tapa).
- La hora de última sync es **por fuente** (`sync_meta.sources`: `last_sync_at` de la última sync buena y `error` del último intento). La sync al abrir se lanza si alguna fuente supera `max_age_hours` o nunca funcionó; una base antigua sin datos por fuente usa la hora global, y al crear la entrada de una fuente por primera vez hereda la global anterior (si no, una primera sync fallida la dejaba en "nunca"). La cabecera muestra una por fuente con ⚠ si el último intento falló.
- `POST /api/sync` responde 202 y corre en segundo plano; el estado vive en memoria (`sync_state`) y la hora de la última sync en la tabla `settings` (`sync_meta`). Se guarda al terminar cada fuente.
- Al guardar ajustes de búsqueda o pesos se recalculan todos los scores (`rescore_all`); también al arrancar el backend, así un cambio en `scoring.py` se aplica con solo reiniciar.
- **El score NO usa LLM** (decisión del dueño: son demasiados coches para gastar tokens en cada uno). Componentes: km, Klimaanlage, TÜV, cabrio/estación, precio vs comparables y cambio (Automatik 10 / Manuell 4 / sin dato 5: el automático se vende más en la Costa del Sol). `services/llm.py` se usa solo en el botón **Analizar rentabilidad**, bajo demanda por coche (ver arriba); El informe de IA vive en `Car.rentabilidad` (JSON). La sync no llama nunca al LLM.
- El componente `precio` compara con el precio esperado del mismo modelo (`scoring.MarketIndex`): modelo hedónico en log-precio con media del modelo ± pendientes por año (≈ +6 %/año) y por km (≈ −0,3 % por 1.000 km), aprendidas de toda la base (regresión intra-grupo; límites y valores por defecto si hay pocos datos). Mínimo 5 coches del mismo modelo, sin contar el propio. 10 puntos si cuesta un 30 % menos que lo esperado, 5 si igual, 1 si un 30 % más. Sin referencia o con modelo genérico ("Andere"), 5 (neutro). Se recalcula en `rescore_all` tras cada fuente. En la base real predice el precio con ≈23 % de error típico (la mediana por año daba ≈26 %). Limitación: el filtro de precio (≤10.000 €) sesga la referencia hacia los ejemplares baratos.
- Los pesos se normalizan. `get_setting` descarta de lo guardado las claves que ya no existen en el código (p. ej. `llm_rentabilidad`); un valor guardado (como `umbral_verde`) pisa al nuevo valor por defecto, así que cambiar un umbral por defecto no afecta a una base ya guardada.
- `ScrapedCar` usa `None` para "sin datos": el upsert ignora `None` y `""` para no pisar datos ya enriquecidos.
